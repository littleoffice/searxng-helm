{{- if not .Values.searxng.existingSecret }}

[secret_key] Auto-generated and stored in Secret/{{ include "searxng.fullname" . }}.
  It is preserved across `helm upgrade` by reading it back from the cluster.
  Argo CD and Flux render with `helm template`, where that read returns nothing
  and the key would be regenerated on every sync, invalidating user sessions.
  If you deploy via GitOps, create the Secret yourself and set:
    searxng.existingSecret: <name>
{{- end }}
{{- if include "searxng.limiterEnabled" . }}

[limiter] Enabled. It attributes requests to the client IP taken from
  X-Forwarded-For, but only when the immediate peer is in
  searxng.limiter.trustedProxies. If that list does not cover your ingress
  controller's pod network, every request looks like one client and the whole
  instance rate-limits itself.
{{- end }}

{{- if include "searxng.relay.fenceKeyEnabled" . }}
  [fence] Signing key from Secret/{{ include "searxng.relay.fenceKeySecretName" . }}, mounted at
    {{ include "searxng.relay.fenceKeyPath" . }}. Every replica signs identically and keeps
    doing so across rollouts. The relay logs a warn line about it at startup:
    a persistent key extends a leak's blast radius from one process lifetime
    to whenever you rotate. Verifiers pin the fingerprint served at
    /fence/public-key (unauthenticated — a public key is public); the image is
    FROM scratch with no shell, so reach it from outside the pod:
      kubectl -n {{ .Release.Namespace }} port-forward svc/{{ include "searxng.relay.fullname" . }} 8080:{{ .Values.mcpRelay.service.port }}
      curl -s localhost:8080/fence/public-key
{{- end }}

    the relay's own `--healthcheck` self-probe instead of an HTTP GET — a
    Kubernetes httpGet probe can only carry a literal header. Anything else
    polling /health (a load balancer, an uptime monitor) must send the token:
      kubectl -n {{ .Release.Namespace }} get secret {{ include "searxng.relay.healthTokenSecretName" . }} \
        -o jsonpath='{.data.{{ include "searxng.relay.healthTokenSecretKey" . }}}' | base64 -d
{{- end }}

{{- if include "searxng.valkey.replicationEnabled" . }}

[valkey] Replication: 1 primary + {{ .Values.valkey.replica.count }} replica(s).
  SearXNG writes to {{ include "searxng.valkey.primaryHost" . }} and has NO
  failover — its client takes a single URL and does not speak Sentinel. If the
  primary is lost you promote a replica by hand:
    kubectl -n {{ .Release.Namespace }} exec {{ include "searxng.valkey.replicaName" . }}-0 -c valkey -- valkey-cli replicaof no one

  resync. Treat the replicas as redundancy and read capacity, not as HA.
